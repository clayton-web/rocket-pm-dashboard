# PM Center External Context Contract — v1

**Status:** authoritative. **Owner:** PM Center. **Consumer:** Rocket Communicator.

This document is the single source of truth for the read-only PM context integration. Rocket
Communicator must not maintain a competing interpretation of this contract; if Communicator needs
behaviour that is not described here, the change belongs in this document and in PM Center first.

Everything below describes **behaviour the implementation actually provides today**. Where the
implementation is limited, the limitation is stated rather than smoothed over.

Rocket Communicator generates work tasks from communications. When it does, it needs to know
*which* PM entity a message is about. This integration gives it a secure way to ask PM Center,
which stays the source of truth. PM Center answers with compact, ranked evidence; Communicator
decides what to auto-link and what to ask a human to confirm.

```
Rocket Communicator
      ↓  server-to-server, Bearer credential
PM Center context resolver
      ↓  Property / Unit / Tenancy / TenancyContact
compact authoritative context response
```

## Scope

- **PM Center does not read Gmail or SMS.** It has no access to Communicator's mailboxes or
  message stores, and this integration adds none.
- **Communicator supplies the lookup hints.** PM Center never receives a full message body, and
  the endpoint has no field to send one.
- **No AI or inference.** Matching is deterministic string canonicalization and exact comparison.
- **Read-only.** No write scope exists. See [Maintenance boundary](#maintenance-boundary).
- **No owner id exists.** PM Center has no Owner model. See [Owner handling](#owner-handling).
- **This is not a public developer platform.** The application identity is a database enum with
  one member (`ROCKET_COMMUNICATOR`).

## Route and versioning

```
POST /api/integrations/v1/context/resolve
Content-Type: application/json
Authorization: Bearer pmctx_<live|test>_<keyId>_<secret>
```

`POST` is the only supported method. Any other method returns **405**, generated by the framework;
its body shape is not part of this contract.

Versioned under `/api/integrations/v1/` to keep server-to-server APIs separate from
`/api/integrations/gmail/*`, which is a staff browser OAuth flow and still requires a session.

### Compatibility rules

The response also carries `version: "v1"`, which matches the path segment. Both are stable.

| Change | Requires a new version? |
| --- | --- |
| Adding a new field to a response object | No — additive |
| Adding a new `matchReason` value | No — additive (see the policy note below) |
| Adding a new candidate collection | No — additive |
| Removing or renaming a documented stable field | **Yes** |
| Changing the meaning or required semantics of a documented stable field | **Yes** |
| Narrowing an accepted request field | **Yes** |

Communicator **must** ignore unknown fields in a response object and unknown members of a
collection rather than failing to parse. Communicator **must** treat an unrecognised `matchReason`
or `confidence` value as *not eligible for auto-link* — see
[Auto-link policy](#auto-link-policy-normative).

**Request fields are a separate case.** Unknown JSON properties in the request body are *currently*
ignored (with the single exception of `organizationId`, which is rejected). That is current
behaviour, **not** a compatibility guarantee: a future version may reject unknown request
properties in order to catch caller bugs, which is exactly why `organizationId` is rejected today.
Communicator should send only the documented fields.

## Authentication

Every request requires `Authorization: Bearer <token>` carrying a PM Center-issued integration
credential with the **`PM_CONTEXT_READ`** scope. There is no session, no cookie, and no anonymous
access.

All authentication and authorization failures return the **same generic `401`** with body
`{"error":"Unauthorized."}`. A caller cannot distinguish "unknown credential" from "revoked",
"expired", "wrong scope", "environment mismatch", or "wrong organization". The specific reason is
written to the PM Center audit log instead. If Communicator sees a `401`, the operational response
is always the same: check the configured credential and escalate to PM Center with the timestamp.

### Organization assertion header

`X-PM-Organization-Id: <organizationId>` is **optional** and is a caller **assertion**, never a
selector. If it disagrees with the credential's organization, the request fails closed with the
generic `401`. There is no request field or header through which a client can choose an
organization. Sending it is recommended: it turns a credential mix-up into an immediate hard
failure instead of silently querying the wrong portfolio.

### Environments

The token's environment segment (`live` for `PRODUCTION`, `test` for `DEVELOPMENT`) is checked
against the `environment` column on the credential's own database row. It is a **label and
consistency check on the issued credential — it is not host pinning.**

Be precise about what this does and does not give you:

- It does guarantee a token cannot be replayed under a *different* environment segment, because
  the stored hash covers the entire raw token including that segment.
- It does **not** prevent a `DEVELOPMENT` credential from working against a production deployment.
  If that credential row exists in the database the production host is pointed at, the credential
  authenticates and reads real data. The prefix is not a technical barrier to that.

Separation is therefore **operational, not cryptographic**. Use separate databases per environment
and issue a separate credential per environment, so a staging deployment is pointed at a database
that has no production data and no production credential rows.

## Organization isolation

The highest-priority requirement of this integration.

The organization is read from the credential row and from nowhere else. Every query is constrained
by that `organizationId` **in the `where` clause itself**. Nothing is fetched by global id and
authorized afterwards, so a record belonging to another organization is indistinguishable from a
record that does not exist — the response is byte-identical.

Models with no `organizationId` column are scoped through their relation to `Property`:

| Model | Constraint |
| --- | --- |
| `Property` | `{ organizationId }` |
| `Unit` | `{ property: { organizationId } }` |
| `Tenancy` | `{ property: { organizationId } }` |
| `TenancyContact` | `{ tenancy: { property: { organizationId } } }` |

The resolver test fixture mirrors Org A's address, unit label, tenant email, and owner email into
Org B, so every isolation test exercises a record that *would* match if scoping failed. The
fixture's fake database throws if any query reaches it without an organization constraint, which
turns "someone removed the scope" into a test failure rather than a data leak.

## Request contract (v1)

```json
{
  "senderEmail": "tenant@example.com",
  "addressHints": ["123 Main Street"],
  "unitHints": ["204"],
  "knownPropertyId": null,
  "knownUnitId": null
}
```

The body must be a JSON **object** (not an array, not a scalar). Every field is optional
individually, but **at least one usable matching signal is required**.

| Field | Type | Limits and behaviour |
| --- | --- | --- |
| `senderEmail` | `string \| null`, omittable | Max **200** characters. Must contain `@` and no whitespace after normalization. An RFC display name is unwrapped (`Jane Doe <jane@example.com>` → `jane@example.com`) and the result is lowercased. `null` / `""` are treated as absent. A non-empty value that is not an email address is a **400**. |
| `addressHints` | `string[]`, omittable | Max **5** entries; each entry max **200** characters after trimming. Entries that are empty after trimming are dropped silently. |
| `unitHints` | `string[]`, omittable | Same limits as `addressHints`. |
| `knownPropertyId` | `string \| null`, omittable | Max **64** characters. `null` / `""` / whitespace-only are treated as absent. |
| `knownUnitId` | `string \| null`, omittable | Same limits as `knownPropertyId`. |
| `senderPhone` | any | **Accepted but never matched in v1.** Reported back in `unsupportedSignals`. See [Unsupported signals](#unsupported-signals). |
| `organizationId` | — | **Rejected with a 400 whenever the property is present, including when its value is `null`.** |

Precise behaviours worth knowing:

- The **5-entry cap is checked before empty entries are dropped.** Sending six entries where two
  are blank is a `400`, not a four-hint request.
- A non-array `addressHints` / `unitHints`, or an array containing a non-string, is a `400`.
- `organizationId` is rejected rather than ignored on purpose. Silently dropping it would hide an
  integration bug on the Communicator side and could leave the caller believing it had selected an
  organization.
- **Usable signal** means: a valid `senderEmail`, **or** at least one surviving `addressHints`
  entry, **or** at least one surviving `unitHints` entry, **or** a `knownPropertyId`, **or** a
  `knownUnitId`. `senderPhone` alone is **not** a usable signal and yields
  `400 "At least one lookup signal is required"`.
- Unknown properties are currently ignored — see [Compatibility rules](#compatibility-rules) for
  why that is not a guarantee.

## Response contract (v1)

`200 OK`:

```json
{
  "version": "v1",
  "requestId": "3f1c9a52-...",
  "unsupportedSignals": [],
  "contacts": [
    {
      "entityType": "tenancy_contact",
      "id": "clx_contact_1",
      "confidence": "high",
      "matchReason": "sender_email_exact_current_tenancy_contact",
      "displayLabel": "Jane Doe — 123 Main Street – 204",
      "contactType": "tenant",
      "occupancy": "current",
      "tenancyId": "clx_tenancy_1",
      "unitId": "clx_unit_1",
      "propertyId": "clx_property_1"
    }
  ],
  "properties": [
    {
      "entityType": "property",
      "id": "clx_property_1",
      "confidence": "high",
      "matchReason": "address_hint_exact_normalized",
      "displayLabel": "123 Main Street",
      "isActive": true,
      "serviceRelationship": "MANAGED"
    }
  ],
  "units": [
    {
      "entityType": "unit",
      "id": "clx_unit_1",
      "confidence": "high",
      "matchReason": "unit_hint_exact_normalized",
      "displayLabel": "123 Main Street – 204",
      "propertyId": "clx_property_1",
      "isActive": true
    }
  ],
  "tenancies": [
    {
      "entityType": "tenancy",
      "id": "clx_tenancy_1",
      "confidence": "high",
      "matchReason": "sender_email_exact_current_tenancy_contact",
      "displayLabel": "123 Main Street – 204",
      "propertyId": "clx_property_1",
      "unitId": "clx_unit_1",
      "status": "active",
      "occupancy": "current"
    }
  ],
  "ownerContactMatches": []
}
```

### Top-level fields

| Field | Type | Notes |
| --- | --- | --- |
| `version` | `"v1"` | Constant for this version. |
| `requestId` | `string` (UUID) | Correlates the response with its PM Center audit row. Contains no PII. **Log it** — it is what PM Center needs to investigate a report. |
| `unsupportedSignals` | `string[]` | Signals the caller sent that this version cannot act on. Currently only ever `[]` or `["senderPhone"]`. |
| `contacts` | `ContactCandidate[]` | |
| `properties` | `PropertyCandidate[]` | |
| `units` | `UnitCandidate[]` | |
| `tenancies` | `TenancyCandidate[]` | |
| `ownerContactMatches` | `OwnerContactMatch[]` | |

**All five candidate collections are always present.** An empty collection is returned as `[]`; it
is never omitted and never `null`.

### Candidate fields

Every candidate in every collection carries `entityType`, `confidence`, `matchReason`, and
`displayLabel`. `displayLabel` is a concise human-readable string for Communicator's UI and never
contains a contact email address or phone number. Type-specific fields:

| Collection | `entityType` | `id` | Additional stable fields |
| --- | --- | --- | --- |
| `contacts` | `"tenancy_contact"` | `TenancyContact.id` | `contactType` (`tenant` \| `co_tenant` \| `occupant` \| `emergency_contact`), `occupancy` (`current` \| `historical`), `tenancyId`, `unitId`, `propertyId` |
| `properties` | `"property"` | `Property.id` | `isActive` (boolean), `serviceRelationship` (`MANAGED` \| `PRE_MANAGEMENT` \| `PLACEMENT_ONLY`) |
| `units` | `"unit"` | `Unit.id` | `propertyId`, `isActive` (boolean) |
| `tenancies` | `"tenancy"` | `Tenancy.id` | `propertyId`, `unitId`, `status` (`TenancyStatus`), `occupancy` (`current` \| `historical`) |
| `ownerContactMatches` | `"property_owner_contact"` | **absent — no owner id exists** | `propertyId`, `ownerContactField: "ownerEmail"`, `isFirstClassOwnerEntity: false` |

`confidence` is `"high" | "medium" | "low"`. `"low"` is reserved and **is never emitted in v1**;
it exists in the union so introducing fuzzy matching later is additive.

`matchReason` is one of:

| `matchReason` | Emitted on |
| --- | --- |
| `sender_email_exact_current_tenancy_contact` | `contacts`, `tenancies` |
| `sender_email_exact_historical_tenancy_contact` | `contacts`, `tenancies` |
| `sender_email_exact_property_owner_contact` | `ownerContactMatches` |
| `known_property_id_authorized` | `properties` |
| `known_unit_id_authorized` | `units` |
| `address_hint_exact_normalized` | `properties` |
| `unit_hint_exact_normalized` | `units` |
| `resolved_unit_current_tenancy` | `tenancies` |

### Ordering and caps

Candidates are sorted so that higher-confidence candidates come first, then capped at **10 per
collection**. Relative order *within* the same confidence tier is not contractual. The response
does not signal that a collection was capped; if Communicator sees 10 candidates it should treat
the set as possibly incomplete and require human confirmation.

### Partial hydration — important

**A resolution does not hydrate every collection.** Communicator must read the ids carried *on the
matched candidate itself* rather than assuming the related entity also appears in its own array.

The email-only case is the one that matters in practice: resolving by `senderEmail` alone can
populate `contacts` and `tenancies` while **`properties` and `units` remain `[]`**. The property
and unit are still identified — they are on the contact candidate as `propertyId` and `unitId`.

Similarly:

- `properties` is only populated by `knownPropertyId`, `knownUnitId` (which also returns the
  parent property), or an address-hint match.
- `units` is only populated by `knownUnitId` or a unit-hint match inside an already-authorized
  property.
- Resolving via `knownUnitId` emits the parent property with `matchReason:
  "known_property_id_authorized"`, even though the caller supplied only `knownUnitId`. The
  authorization is equivalent — the parent was reached through an organization-scoped lookup of the
  caller's own unit id.

### Fields intentionally omitted

The response carries identifiers, a display label, and match evidence. It never includes:

application income, employer or job title, employment notes, credit-check consent, consent
signature name, consent IP address or user agent, security or pet deposits, monthly rent, lease
setup blobs, signatures, documents or storage keys, emergency contact details, `ClientProfile`
records, internal staff notes, `Property.strataNotes`, `Property.ownerEmail`/`ownerPhone` values,
Buildium resident center URLs, broad staff data, or any secret.

Contact and owner **email addresses and phone numbers are not returned** either — including the
sender's own. Communicator already has the sender address; PM Center does not echo it back.
`lib/integrations/pm-context/resolve-context.test.ts` asserts these absences.

Contacts are returned only for the sender who matched. Resolving a unit by address does **not**
return the names of people living there.

There is also an internal `diagnostics` object inside the resolver (currently
`propertyScanTruncated`). It is written to the audit log and is **deliberately not part of the
response**. It is not part of this contract and Communicator must not depend on it appearing.

## Matching and confidence semantics

Deterministic and conservative throughout. No LLM, no edit distance, no token-overlap scoring. A
hint that does not canonicalize to an exact stored value produces no candidate.

**Sender email.** Normalized by lowercasing and unwrapping an RFC display name. Compared
case-insensitively against current `TenancyContact` rows, historical `TenancyContact` rows, and
`Property.ownerEmail`. Current and historical matches are never mixed: each candidate carries its
own `occupancy`, and a historical match can never be reported as current.

**Known ids.** `knownPropertyId` and `knownUnitId` are resolved with the organization in the
`where` clause. A record belonging to another organization returns no match.

**Address and unit hints.** `normalizeStreetLineKey` lowercases, strips punctuation, collapses
whitespace, and expands a fixed list of standard street types (`St`→`Street`, `Ave`→`Avenue`,
`Cres`→`Crescent`, …) and directionals (`W`→`West`, `NE`→`Northeast`, …). This is canonicalization,
not fuzzy matching: `123 Main St` and `123 Main Street` are the same address written differently,
while `123 Maine St` and `12 Main St` stay distinct.

Unit hints are resolved **only inside already-authorized properties** (reached via
`knownPropertyId`, `knownUnitId`, or an address match). A bare unit hint with no property scope
returns nothing.

### Confidence

A small explicit category derived from deterministic evidence. It is **not** a probability and
**not** a computed score.

| Confidence | Evidence |
| --- | --- |
| `high` | Exact sender email resolving to exactly one *current* tenancy contact; an authorized known property or unit id; an exact normalized address matching exactly one property; an exact property plus exact unit resolving to one record |
| `medium` | Owner email match; exact sender email mapping to several current records; any historical tenancy contact; exact property with an ambiguous unit |
| `low` | Reserved for fuzzy address candidates; never emitted in v1 |

Confidence describes **identification certainty**, not actionability and not authorization. An
inactive or placement-only property still matches at `high` if the address uniquely identifies it —
`isActive` and `serviceRelationship` are returned so Communicator can decide what to do.

## Auto-link policy (normative)

> **Confidence is descriptive evidence, not authorization to auto-link.** A candidate is eligible
> for automatic linking only when its `matchReason` **and** candidate type also satisfy the rules
> below. `confidence: "high"` alone is **not** sufficient and must never be used as the criterion.

This matters concretely: an address-hint match against a uniquely-identified property returns
`high`, and a unit-hint match inside it returns `high`, and the unit's current tenancy is then also
returned at `high`. None of those are safe to link automatically, because normalizing an address
string is not the same as knowing the message is about that address.

Eligibility is evaluated **per candidate**, not per response. A single response can contain one
auto-linkable candidate and several that require confirmation.

### Communicator MAY auto-link

1. **An authorized known id it supplied itself.** A `properties` candidate with `matchReason:
   "known_property_id_authorized"`, or a `units` candidate with `matchReason:
   "known_unit_id_authorized"`. These are PM Center confirming that an id Communicator already
   held belongs to the credential's organization.

2. **A unique current tenancy-contact email match.** A `contacts` candidate where **all** of the
   following hold:

   - `matchReason === "sender_email_exact_current_tenancy_contact"`, **and**
   - `occupancy === "current"`, **and**
   - `contactType === "tenant"` **or** `contactType === "co_tenant"`, **and**
   - `confidence === "high"` (PM Center emits `high` here only when exactly one current tenancy
     contact matched — several current matches are downgraded to `medium`), **and**
   - it is the **only** candidate in `contacts` meeting the four conditions above.

   When this qualifies, Communicator may link to the `tenancyId`, `unitId`, and `propertyId`
   carried **on that contact candidate**.

### Communicator MUST require human confirmation

- `address_hint_exact_normalized` — any confidence. See
  [Address-hint limitation](#address-hint-limitation).
- `unit_hint_exact_normalized` — any confidence.
- `resolved_unit_current_tenancy` — any confidence; it inherits the confidence of the unit that
  produced it, so it can be `high` while resting on an address hint.
- `sender_email_exact_property_owner_contact` and every `ownerContactMatches` entry — there is no
  owner entity to link to.
- `sender_email_exact_historical_tenancy_contact` and any candidate with
  `occupancy === "historical"` — the person used to live there.
- Any candidate with `contactType` of `occupant` or `emergency_contact`, unless a future version of
  this contract explicitly promotes them.
- Any ambiguous or multiple match — including more than one qualifying contact candidate, or a
  collection returned at the 10-candidate cap.
- Any candidate with `confidence` of `medium` or `low`.
- **Any `matchReason` or `confidence` value not explicitly listed in the allowlist above**,
  including values introduced by a future PM Center release. New match reasons are additive and do
  **not** automatically join the allowlist; adding one to it requires a documented update here.

This last rule is what keeps the policy forward-compatible: PM Center can introduce new `high`
match reasons without silently widening what Communicator links without a human.

### Regardless of auto-link

- Always check `occupancy` before describing someone as the current tenant.
- Check `isActive` and `serviceRelationship` before treating a property as actively managed.
- Store PM Center CUIDs (`propertyId`, `unitId`, `tenancyId`, contact `id`) as the durable link. Do
  not replicate PM data — re-resolve or fetch when context is needed.
- Read `unsupportedSignals`; do not assume a signal was used just because it was accepted.

## Address-hint limitation

**Send the street/property address in `addressHints` and the unit identifier separately in
`unitHints`.** This is the supported shape and the one Communicator should build against.

```json
{ "addressHints": ["123 Main Street"], "unitHints": ["204"] }
```

The normalizer does recognise two embedded unit-in-address forms — a leading `204-` before a street
number, and a leading `#204 ` before a street number — but **Communicator should not rely on them
for linking.** A hyphenated leading number is genuinely ambiguous: `204-123 Main St` is a unit in a
building, while a civic range such as `100-200 Main St` is a single property spanning street
numbers. The current normalizer cannot tell them apart and will read the leading number as a unit
in both cases.

This ambiguity is one of the reasons address matches require confirmation in v1 (see the
[auto-link policy](#auto-link-policy-normative)). Improving the civic-range parser is a
carry-forward; it is not a blocker, because no address-derived candidate is auto-linkable.

## Error contract

| Status | Meaning | Body | Safe to retry? |
| --- | --- | --- | --- |
| `400` | Malformed JSON, or a request/schema/validation failure | `{"error": "<message>"}` | **No.** Fix the caller. Retrying the identical body always fails identically. |
| `401` | Authentication or authorization failure — intentionally generic | `{"error": "Unauthorized."}` | **No**, not without operator action. Re-check the configured credential. |
| `405` | Method other than `POST` | framework-generated | **No.** |
| `429` | Rate limited | `{"error": "Too many requests. Try again later."}` plus a `Retry-After` header in seconds | **Yes**, after honouring `Retry-After`. |
| `500` | Internal resolution failure | `{"error": "Context resolution failed.", "requestId": "<uuid>"}` | **Yes**, with backoff. Report the `requestId` to PM Center. |

Notes:

- **Error bodies carry English prose, not machine-readable codes.** Communicator must branch on the
  **HTTP status**, never on the `error` string. Adding a stable machine-readable code is a possible
  future additive change; it does not exist today.
- The `400` message names the offending field (for example `addressHints accepts at most 5 values`)
  and is intended for a developer reading a log, not for programmatic parsing.
- `500` never echoes the underlying error, because it can contain organization data. The full error
  is logged server-side against the same `requestId` returned to the caller. `requestId` is present
  on `500` and on `200`; it is **not** present on `400`, `401`, `405`, or `429`, because those fail
  before a request id is assigned.

## Rate limits

Two independent fixed-window limiters apply to every request, **in this order**:

| Order | Limiter | Key | Default | Override |
| --- | --- | --- | --- | --- |
| 1 | Pre-authentication | client source IP | **20 / minute** | `PM_CONTEXT_AUTH_RATE_LIMIT_PER_MINUTE` |
| 2 | Post-authentication | credential id | **60 / minute** | `PM_CONTEXT_RATE_LIMIT_PER_MINUTE` |

**The effective limit for Communicator is not 60/minute.** The IP limiter runs first, counts *every*
request (not just failed ones), and at its default is the **binding constraint** for traffic
arriving from a single source IP: roughly **20 requests per minute per source IP**. The 60/minute
per-credential limit only becomes the binding one when Communicator's traffic is spread across more
than three source IPs. Plan capacity against 20/minute/IP.

The pre-auth limiter exists to bound credential guessing and the audit writes that failed
authentication produces. The per-credential limiter is keyed by credential id so one integration
client cannot starve another.

Both return `429` with `Retry-After`. Communicator should honour `Retry-After` and back off rather
than retrying immediately.

**Honest limitation:** both limiters are **in-process and per-instance**. They are not globally
distributed. On serverless they reset on cold start and are not shared across instances, so the
observed limit is roughly the configured value multiplied by the number of live instances. This is
real abuse protection, not a hard guarantee. A distributed limiter (Redis or edge/WAF) is the
correct fix and is a deliberate carry-forward for the read-only v1 phase; no new dependency was
added here. This is the same constraint already documented for the rest of the app in
`docs/deployment-checklist.md`.

One further detail: the IP key is derived from `x-forwarded-for` / `x-real-ip` and falls back to a
literal `unknown` bucket when neither is present, so requests reaching the app without proxy
headers share a single bucket.

## Unsupported signals

`senderPhone` may be supplied — the schema accepts it and it does not cause a validation error.
However:

- **PM Center does not use it for resolution.** No candidate is ever produced from phone data.
- Whenever a non-empty `senderPhone` is sent, the response reports it:
  `"unsupportedSignals": ["senderPhone"]`.
- `senderPhone` is **not** a usable matching signal. A request whose only signal is `senderPhone`
  is rejected with `400 "At least one lookup signal is required"`.
- **Communicator must not infer a match from phone data in v1.**

Why it is unsupported rather than badly supported: the repository has no phone normalization
anywhere, and `TenancyContact.phone` / `Property.ownerPhone` are free-form strings written by
several intake paths. Matching them safely needs a normalized column, a backfill, an index, and
updates to every write path. Comparing raw strings would be unreliable, so the signal is reported
as unsupported rather than matched badly. There is also no consumer yet — SMS is not part of this
phase.

`unsupportedSignals` is the general mechanism, not a phone-specific one. Communicator should read
it on every response and treat any listed signal as ignored.

## Maintenance boundary

This v1 context endpoint is **strictly read-only**. Specifically, it:

- does **not** create maintenance requests;
- does **not** update, create, or delete any PM Center entity;
- does **not** provide maintenance history or any maintenance context;
- does **not** grant any write capability — `PM_CONTEXT_READ` is the only scope that exists in the
  schema, and there is no write scope to grant.

There is deliberately no placeholder maintenance field in the response, to avoid shipping dead
contract surface.

Future maintenance actions must be delivered as **separately scoped command endpoints** with their
own scopes and explicit idempotency semantics. They are not designed here and must not be inferred
from this contract.

## Known v1 limitations

1. **Phone matching is not implemented.** See [Unsupported signals](#unsupported-signals).
2. **Embedded unit / civic-range parsing is ambiguous.** See
   [Address-hint limitation](#address-hint-limitation).
3. **Fuzzy address matching is not supported**, so `low` confidence is never returned and a hint
   that does not canonicalize exactly produces no candidate.
4. **Rate limiting is in-process and per-instance**, and the binding limit is the 20/minute IP
   limiter. See [Rate limits](#rate-limits).
5. **Address matching scans organization properties in memory.** Street lines are stored raw, so
   there is no index on the normalized form. When every hint has a leading street number the query
   narrows with `startsWith` on that number; otherwise it scans up to `MAX_ORG_PROPERTY_SCAN`
   (2000) properties for the organization. Fine at current portfolio sizes; a normalized, indexed
   street key is the scalable fix. Truncation is recorded in the audit log, not in the response.
6. **Collection caps are silent.** A collection is capped at 10 with no truncation flag.
7. **No maintenance context**, by design.
8. **No owner entity.** See [Owner handling](#owner-handling).
9. **`lastUsedAt` makes a read-only endpoint write.** Throttled to at most one write per minute per
   credential.
10. **No admin UI for credentials.** Issuance is the CLI script below.
11. **Environment separation is operational, not cryptographic.** See
    [Environments](#environments).

## Operating the integration

Everything below this line is PM Center operational detail. Communicator integrators need the
credential handoff steps; the rest is for PM Center maintainers.

### Credential model

`IntegrationCredential` binds one credential to exactly one `Organization`:

| Field | Purpose |
| --- | --- |
| `id` | Stable credential id, used in audit rows |
| `organizationId` | The only organization this credential can ever read |
| `app` | `ROCKET_COMMUNICATOR` |
| `environment` | `PRODUCTION` / `DEVELOPMENT` |
| `name` | Human-readable admin label |
| `keyId` | Public lookup handle embedded in the token (24 hex chars, indexed unique) |
| `secretHash` | SHA-256 of the full raw token |
| `scopes` | `PM_CONTEXT_READ` |
| `createdByUserId` / `revokedByUserId` | Issuing and revoking administrator |
| `lastUsedAt` | Throttled to at most one write per minute per credential |
| `expiresAt` | Optional; expiry is inclusive (`expiresAt <= now` is expired) |
| `revokedAt` | Revocation timestamp; checked on every request with no caching |

### Secret generation, storage, and verification

The raw token is `pmctx_<live|test>_<keyId>_<secret>`, where the environment segment is `live` for
`PRODUCTION` and `test` for `DEVELOPMENT`, `keyId` is 12 random bytes as hex (24 characters), and
`secret` is 32 random bytes (256 bits) from `randomBytes` as base64url. `keyId` is hex so it can
never contain the `_` separator; the parser treats everything after the third separator as the
secret, because base64url can.

- The raw token is returned **once**, at creation, and is never stored, logged, or recoverable.
- Only `keyId` and `secretHash` are persisted. `secretHash` is SHA-256 of the *entire* raw token,
  so a secret cannot be replayed under a different environment segment or key id.
- Verification looks the credential up by `keyId`, then compares hashes with `timingSafeEqual`
  (the same pattern as `lib/leasing/lease-signing-token.ts` and the tenant OTP store).
- The secret hash is verified **before** environment, revocation, expiry, scope, and organization
  assertion are checked, so a caller holding only a key id cannot probe whether a credential exists
  or what state it is in.
- Secrets never appear in logs. Audit rows record `keyId` and the credential id only.
- This credential is independent of `CRON_SECRET`, `JOB_PROCESSOR_SECRET`, NextAuth secrets, the
  tenant portal OTP secret, Gmail OAuth credentials, and Buildium credentials. Nothing is reused.

A lost token cannot be recovered. Revoke it and issue a new one.

### Scopes

`PM_CONTEXT_READ` is the read-only scope, equivalent to `pm:context:read`. It is the only scope
that exists. There are no write scopes and no maintenance scopes in this phase.

### Creating and revoking

Issuance runs through `lib/integrations/pm-context/integration-credential.service.ts`, guarded by
`requireOrganizationAdmin`. Only organization ADMIN/OWNER can issue, list, or revoke, and the
organization always comes from the administrator's `StaffContext` — there is no parameter to issue
a credential for a different organization.

`scripts/integration-credential.ts` is the operational surface. It loads a real `StaffContext` for
the named administrator, so running the script does not bypass the authorization rules.
`CREDENTIAL_ENVIRONMENT` defaults to `PRODUCTION` when unset; set it explicitly.

```bash
# Issue (prints the raw token once)
ORGANIZATION_SLUG=axford \
ADMIN_EMAIL=admin@example.com \
CREDENTIAL_NAME="Rocket Communicator (production)" \
CREDENTIAL_ENVIRONMENT=PRODUCTION \
npx tsx scripts/integration-credential.ts issue

# List
ORGANIZATION_SLUG=axford ADMIN_EMAIL=admin@example.com \
npx tsx scripts/integration-credential.ts list

# Revoke
ORGANIZATION_SLUG=axford ADMIN_EMAIL=admin@example.com CREDENTIAL_ID=clx... \
npx tsx scripts/integration-credential.ts revoke
```

Revocation takes effect immediately: `revokedAt` is read from the database on every request and
nothing is cached, so the next call after revocation fails.

### How Rocket Communicator receives and stores the secret

1. A PM Center organization administrator issues a credential with the script above and copies the
   raw token from the terminal.
2. The token is transferred out of band (a password manager or secret-sharing link, not email or
   chat) to whoever configures Communicator.
3. Communicator stores it in its own server-side secret store or platform environment variable
   (for example `PM_CENTER_API_TOKEN`). It must never reach a browser bundle, a client-side config,
   a log line, or version control.
4. Issue separate `DEVELOPMENT` and `PRODUCTION` credentials, and point each Communicator
   environment at a PM Center environment with its own database. The environment segment in the
   token is a consistency label, not a technical barrier — separation comes from the database and
   deployment, not the prefix.
5. Rotation is issue-then-revoke: create the new credential, deploy it, then revoke the old one.

### Audit logging

Written to the existing `AuditLog` table. `AuditLog.actorUserId` is nullable and an
`integrationCredentialId` column carries the machine principal, because a server-to-server client
has no staff user.

| Action | Actor | Recorded |
| --- | --- | --- |
| `integration.pm_context.resolved` | credential | `requestId`, app, environment, signal presence, result counts, match reasons, matched property/unit/tenancy ids, `propertyScanTruncated` |
| `integration.auth.failed` | credential (once identified) | failure reason, route, `keyId` |
| `integration.rate_limited` | credential | route |
| `integration.credential.created` | admin user | app, environment, scopes, expiry |
| `integration.credential.revoked` | admin user | credential id |

Never logged: the raw credential, the secret hash, the request body, message content, or the
sender's email or phone. Lookup signals are recorded as booleans and counts (`hasSenderEmail`,
`addressHintCount`) so usage can be investigated without storing PII. Matched **ids** are recorded;
matched **values** are not.

Audit writes are best-effort and never block a response: a failed audit write is swallowed so it
cannot turn a successful resolution into a `500`.

## Implementation notes

### Middleware boundary

`middleware.ts` skips the **staff session check** for `/api/integrations/v1/*`. These routes are
not public: each authenticates its own bearer credential before doing any work. This exemption is
deliberately separate from the cron route exemption — cron and integrations use different
credentials and must not share a bypass. `isIntegrationApiV1Path` is unit-tested against lookalike
paths, including `/api/integrations/gmail/*`, which must keep its session requirement, and
`/evil/api/integrations/v1/...`, which must not match.

### Current vs historical tenancy

`lib/leasing/tenancy-occupancy.ts` is the single source of truth:

- **current**: `pending_move_in`, `active`, `notice_received`, `move_out_scheduled`,
  `inspection_scheduled`, `inspection_completed`
- **historical**: `ended`, `archived`

`pending_move_in` is current because the unit is already committed to an incoming tenancy.
Everything through `inspection_completed` is still an in-progress occupancy lifecycle.

This rule previously existed twice, in `lib/property/property-tenancies-staff.ts` and
`lib/leasing/rental-listing-active-tenancy.ts`. Both now import it, and a test asserts the rental
listing publish guard agrees with the occupancy rule for every `TenancyStatus`.

### Owner handling

PM Center has **no Owner model**, and this slice does not add one. `Property.ownerEmail` is an
unstructured property-level contact field.

An `ownerContactMatch` therefore carries a `propertyId` but **no `id`**, plus an explicit
`isFirstClassOwnerEntity: false` and `ownerContactField: "ownerEmail"`. No owner id is invented,
and Communicator must not synthesize or persist an owner identity from this — associate with the
`propertyId` instead. Organization-wide landlord-of-record fields on `Organization` are not
exposed: they describe the management company, not the property owner.

A first-class owner entity is a carry-forward, not a v1 gap to work around.

### Carry-forwards

Known, accepted, and deliberately not addressed in v1: civic-range parser improvement; SQL-level
filtering of current tenancy statuses instead of fetching then filtering in JS; distributed rate
limiting; an admin credential UI; occupancy enum exhaustiveness; additional HTTP-level test
coverage; hardening the `CREDENTIAL_ENVIRONMENT` default; future maintenance scopes; and a
first-class owner entity.
